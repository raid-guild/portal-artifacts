# Dune Relay gifts (phase 2)

## Player rules

Portal accounts earn a five-day daily cycle simply by opening the online game. Playing a level or claiming a gift is not required to count the visit. Days use UTC and reset at 00:00 UTC: day 1 gives 100 coins, day 2 gives 200, day 3 gives two independently selected starting power-ups, day 4 gives 500 coins, and day 5 gives 1,000. The next consecutive visit starts at day 1 again; missing a UTC day also resets to day 1. The day 3 pool is Water Jet, Flywheel, and Prism, with Tile Bomb and Free Swap added once Farmland is canonically unlocked. Duplicate selections give two of the same item. The server freezes that day's selection on the visit, before claiming, so refreshing or retrying never rerolls it. A missed daily gift expires. Guests are not eligible for daily gifts in this phase.

Each completed chapter offers a separate, one-time gift of 200 coins and one inventory item: Oasis → Water Jet, Open Desert → Flywheel, River Gatehouse → Prism, Farmland → Tile Bomb, Town on the Hill → Free Swap, Castle Island → Flywheel, River Journey → Prism. Earlier chapter completions qualify, including imported demo progress. Replays do not create more gifts. The existing one-time Fieldkeeper toolkit is a separate reward and remains available to eligible players.

Gifts are offered in the home and map views and listed in Settings → Gifts. The inbox shows the current day of five even after claiming, and collects multiple unclaimed gifts without interrupting play with a series of dialogs. Opening a parcel reveals its exact coin and item award, then Continue marks the reveal as seen. Maybe later leaves an unpresented award in the inbox. Playtest Settings offers repeatable daily and chapter gift previews with a transient preview total; previews do not write campaign coins, inventory, account cache, or API data. Level achievements and offline claiming are deferred.

## Server contract and recovery

The reward catalog is versioned independently of the campaign content version. Version 2 adds the five-day cycle. Its identity keys (`daily:YYYY-MM-DD`, `chapter:oasis`, etc.) are stable; a later catalog revision does not regrant an existing key. Existing version 1 daily claims keep their original 100-coin award. A version 1 claim today counts as day 1; a claim yesterday seeds today's visit as day 2. The server derives chapter eligibility from the canonical completed prefix and ignores client-supplied amounts. Each award is stored in `dune_reward_claims` with an immutable payload, claim time, and optional presentation time. A mixed item award uses the `items` array as its complete item grant; older single-item awards retain their `item` and `quantity` pair. The account profile and ledger grant are committed in one player-locked transaction. Both coins and inventory are capped at 1,000,000; a full balance rejects the entire claim without marking it claimed. A rejected claim does not erase or reroll the reserved daily award.

`POST /leaderboard-api/dune-relay/rewards/visit` reserves today's streak day and award under the player lock. It changes only server-owned daily visit metadata, not the economic revision, so it does not stale an active level attempt. The client calls it after resolving the Portal account on opening, on a visible return to the app, when coming online, and at UTC rollover while visible. A hidden overnight timer alone does not count a visit. `GET /rewards` is read-only: it returns today's server day, next reset, cycle status, offer status, and all claimed but unpresented awards, without choosing random items. `POST /rewards/claim` takes a UUID request ID and a reward key; an old client can reserve today's visit before the claim transaction. Duplicate requests and duplicate keys cannot grant twice. Its response returns the immutable award and the current locked profile even when an old operation receipt is replayed. `POST /rewards/presented` acknowledges a claimed award idempotently without changing balance or profile revision. Account, Origin, and authentication checks follow the existing Dune API rules.

The client stores the account-scoped claim request before sending it. A lost response leaves the same request ID available for retry; a committed claim also appears in the server's unpresented list after a reload or loss of browser storage. It fetches the current campaign after a claim receipt before applying the balance, and does not overwrite newer Portal progress with an old receipt. Startup reconciles existing gift requests before deciding whether to offer guest import, so postponed reveals do not remove that choice. An uncertain claim blocks starting a new level until resolved. Deterministic 400/403/409 rejection releases the local pending request; network errors retain it. Offline claims are unavailable. If the backend does not yet expose `/rewards`, the game continues without Gifts.

A daily visit or gift may create a Portal profile before the player imports a guest campaign. `GET /campaign` supplies a server-derived `canImportGuest` hint. The import endpoint checks it again while holding the player lock. An account with only daily reward claims, the exact ledger-derived coin and inventory totals (including mixed item grants), no attempts, and no prior gameplay/import/checkpoint operation may still import once. Import adds validated guest coins to the earned daily coins and preserves inventory, daily visit metadata, and reward ledger. An explicit fresh start or other campaign activity closes this import path. This is a narrow first-import exception, not a general save merge.

## Rollout

Run `npm run migrate` in `services/leaderboards` using database-owner credentials, then apply the updated runtime grants in `ops/dune-grants.sql` **before** deploying the backend. The backend Docker start command does not migrate. Deploy the backend, verify `/leaderboard-api/dune-relay/ready` for `dune_reward_claims` and its required columns and grants, then release the static game artifact. The five-day extension needs no additional SQL table or grant beyond the phase 2 ledger migration; its daily visit metadata lives in the profile JSON. Roll out the backend before the game client. An older backend without `/rewards/visit` leaves gameplay available and gifts on the older behavior. Keep campaign Save v5, cloud cache v1, and content version `chapter-7-4`. No live migration or deployment was run during implementation.


## Verification

Focused five-day API tests cover visit progression without claims, day 5 rollover and missed-day reset, frozen draws and capacity retry, legacy daily rows, Farmland pool expansion, and mixed-item guest import. Verification also covers hidden startup, foreground visits during a restored board, missed-day reset, mixed and duplicate reveals, five-day rollover, guest import, and recovery of older unpresented gifts. Run `npm run test:streak-browser` alongside the existing rewards browser suite. The full API suite passed 127 tests, the focused simultaneous-visit test passed, and the core suite passed.
